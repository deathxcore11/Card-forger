## Concrete findings

The Phase WASM bridge exposes card loading, deck compatibility, format gates,
game initialization, action submission, viewer-filtered state, legal actions,
payment previews, state export/restore, replay export and CPU proposals. These
are available APIs; the limited execution evidence below covers only a subset. A large generated card catalog is not proof that each card
is executable and rules-correct.

Two defaults require explicit treatment before any CPU adoption:

1. `config.rs` sets `determinization_samples: 0` in the difficulty presets and
   tests that choice. `determinize.rs` explicitly describes it as
   perfect-information search. `search.rs` takes the unsampled authoritative
   state path when K is zero. Using this opponent unchanged would violate our
   no-hidden-hand/no-future-draw requirement. Enabling sampling alone is not a
   privacy proof; sampling pools, known/revealed cards, own-library order,
   candidate generation, evaluation and logs all need adversarial review.
2. `get_ai_action_proposal` constructs `rand::rng()` in the WASM bridge. A seeded
   game shuffle does not thereby provide a recorded, reproducible CPU decision
   stream. A chosen adapter/policy needs an explicit deterministic decision
   seed/version and bounded execution contract.

For this source revision, `export_game_state_json`, `restore_game_state` and
`resume_restored_game_state` exist. Their presence does not prove that all
pending decisions, random state and CPU session state survive a cold restart.

At the initial source audit the environment had no Rust/cargo/wasm-pack
toolchain. The read-only checkout succeeded; a direct request to the project's
preview website returned HTTP 403. No candidate build, WASM startup, match,
timing benchmark or offline test was completed then. That access response is
not a diagnosis of the project's deployment or intended-device support.

October 24 follow-up: the pinned `nightly-2026-04-19` toolchain, wasm32 target
and wasm-bindgen CLI 0.2.121 are now installed in an isolated research directory.
The original two-job `wasm-dev` build reached the engine/CPU crates but its
engine compiler was killed at the container's 8 GiB limit (`SIGKILL`, confirmed
`oom_kill = 1`). A serial build with optimization and debug information disabled
was also killed at the same memory limit (cumulative `oom_kill = 2`).
Neither build produced a runtime artifact. This says nothing about game-time
RAM or device performance. The [CPU proposal review](4.0-cpu-proposal-review.md) records the research,
corrected architecture claims and required tests. No runtime is adopted.

The top-level license files are only an initial rights check. Before adopting a
candidate, retain its dependency notices and resolve the exact executable card
data/assets and distribution requirements. No paid runtime or new license
commitment has been made.

## Executable checkpoint: narrow smoke test passed

A completed `wasm` artifact from upstream run `40129115223`, artifact
`12574954346`, matched the exact source commit above. Its ZIP SHA-256 was
verified against the artifact metadata before extracting the engine only.
The engine WASM is 40,060,780 bytes; offline package/hosting size remains a
real adoption consideration. It has not been added to product assets.

The [optional diagnostic](../experiments/phase-engine/README.md) verifies
JS/WASM/fixture hashes before execution and records its captured
[evidence](../experiments/phase-engine/evidence-2026-10-24.json):

- Bootstrap and card loading succeeded with a three-record upstream fixture.
  The decks use Forest and Grizzly Bears, not the unused Lightning Bolt.
- Three seeds × two starting-player settings completed: 384–930 accepted
  actions, terminal turns 22–57, engine GameOver in all six. Both seats used a
  simple legal-choice policy with its own saved RNG; no graded/default AI ran.
- A fresh Node process restored the first game's action-80 Priority choice and
  reproduced its entire accepted-action suffix, final turn and terminal result.
- Parent and resumed process made zero fetch calls under a throwing guard.
  This is not browser cold-start airplane-mode evidence.
- Initial filtered states in both seats redacted unknown names/card IDs and
  zeroed game RNG seed/position. Ordered opaque library IDs remained. Full
  observation equivalence, reveal-history and candidate/log privacy are unproved.

The two lists are unequal, intentionally land-heavy 60-card lists using the
engine's Modern configuration. They are not a shipping pool or evidence of
contextual deck strategy. All six winners were seat 1. These results do not
establish balance, seat symmetry, independent rules correctness, broad card
coverage or measured gameplay responsiveness. No default CPU adoption follows.

## Coin and pregame source audit

The October 24 reference follow-up requires real coin outcomes and finished
presentation. At the same pinned source, `game/effects/flip_coin.rs` draws
`RandomDraw::Outcome` from the seeded game RNG and emits
`CoinFlipped { player_id, won }`. Multiple/replaced flips can pause at
`CoinFlipKeepChoice`; `engine_resolution_choices.rs` checks the selected count,
distinct indices and range before resuming. Upstream integration tests cover
apply-driven suspension and persisted-wire restoration, but were only read,
**not run by CardStashy**. The six Forest/Bears games exercised none of this.

Adoption gaps remain: the inspected coin wire records win/loss, not a distinct
player heads/tails call; `UntilLoss` has a 1,000-win cap that finishes/pays rather
than establishing arbitrary coin-loop rules fidelity. Pregame `start_game`
emits a seeded d20 `StartingPlayerContest` and explicitly makes the winner start
without offering the play/draw choice. A coin animation must not disguise that
die contest or the missing choice. Exact supported effects, authoritative
pregame/call contracts, replay and presentation need new fixtures/sign-off.

## Remaining executable proof

Keep the integration isolated from the app and current APK. Freeze a candidate
source revision and reproducible build first. Then use a diagnostic harness to:

1. Load two explicitly versioned supported decks; independently preflight their
   construction, card execution and CPU pilotability.
2. Run seeded complete games in both seats. Retain accepted-action traces,
   terminal reasons and decision/resource bounds. A diagnostic cutoff fails or
   remains inconclusive; it does not create a winner.
3. Change hidden hands and library orders while holding permitted observation
   and CPU decision seed constant. Verify unchanged decisions and no private
   data in UI, hints or logs.
4. Export at human choices, CPU choices, stack decisions and payment previews;
   terminate the runtime, restart offline, restore and continue without duplicate
   actions or results.

The smoke test supplies partial evidence for item 2 and one Priority restore
in item 4. Release-scope decks/preflight, tactical and privacy assertions, all
required pending choices, browser cold-offline recovery and idempotent results
remain open. The first shipping constructed format/card pool and Draft product
also remain unresolved. Do not enable Play or reinterpret the two
proof decks as support for every generated deck.

## Separate Play branch: mechanic execution and response blocker

The follow-up uses 18 unchanged exported records from the exact pinned source's
tracked `integration_cards.json.gz` (SHA-256
`0dbc4d30f035ffc538bf8ae904dbfdc815e9bb53371c05797361b2b639ede2b9`).
Engineered persisted-state setups are explicitly labeled; they are not legal
full-game histories. No external card data or runtime is committed.

Actual WASM checks now pass Head Games's correct opponent/search/shuffle and
fresh-process pending-search recovery, Raise the Alarm's two distinct Soldiers,
Parallel Lives's four Soldiers, Lightning Bolt's three damage, an opponent's
Counterspell response preserving life, and three explicit Basalt Monolith /
Power Artifact cycles with net mana totals 2/4/6.

**Ninjutsu fails the required response-window regression.** The accepted
activation pays mana and returns the attacker, but immediately places the Ninja
on the battlefield with zero stack entries and no StackPushed event. This is
an engine-adoption blocker, not a supported mechanic. The optional mechanics
command intentionally exits nonzero until this requirement passes.

Pinned source anchors: `game/engine.rs` ActivateNinjutsu dispatch around line
15754, `game/keywords.rs::activate_ninjutsu` around line 933. A future correction
must split cost announcement from entry resolution through an actual typed
stack action, preserving source zone/incarnation, defender, replacement-entry
continuations and persisted recovery. Countering the ability must retain paid
costs while preventing entry. A UI delay or fabricated opponent response would
not fix the authoritative state. No patched source/binary has been built.

The Head Games case also proves that candidate enumeration is not exhaustive:
a valid chosen pair absent from generated candidates was accepted by the engine.
A general human selector must use authoritative rules validation and correct
choice constraints; AI candidate membership alone is insufficient. The narrow
Forest/Bears human command experiment remains explicitly bounded.
