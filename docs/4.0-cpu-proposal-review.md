# Local CPU proposal — engineering review

Reviewed October 24, 2026 against the current CardStashy source, the pinned
Phase engine candidate and primary research. The proposed local scoring CPU is
useful direction. It does not establish that a rules adapter, gameplay board,
auto-tapper, game log or right-side game inspector already works in CardStashy.
No CPU difficulty or complete supported card pool is certified by this review.

## Decision

Keep the separation between authoritative rules, a local CPU decision policy,
and event-driven presentation. No cloud language model is required for the
opponent. Reuse CardStashy's exact card identities, deck construction evidence,
local learning material and versioned deck plans as inputs where relevant.

Change the promises about zero latency, complete metadata being sufficient,
fixed search depth, unseeded mistakes and win probabilities. Those need bounded
contracts and measured evidence.

## What helps, and what needs correction

| Proposal | Assessment and required treatment |
| --- | --- |
| One legal-action generator for all difficulties | Keep. CPU decisions use permitted observations and engine-approved choices. A proposal must still be revalidated against the live seat/revision before application. |
| Use the offline wiki as the source of truth | Printed text supports explanations and strategy hints. Executable rules and current engine state decide targets, costs, layers, damage, counters, attachments, triggers and outcomes. Deck roles do not execute Oracle text. |
| Easy/Medium/Hard differ by intelligence | Keep the same rules/information rights. Vary bounded planning, evaluation and sequencing. Player help remains a separate setting, as already approved. |
| One/two/three steps of lookahead | Treat as an initial hypothesis, not turns or a strength guarantee. A step might be a priority pass, target choice, trigger decision or payment; branching and useful tactical horizons differ. |
| Hard uses alpha-beta | Potential inner technique for appropriate two-player searches. Hidden cards and random draws require an information model; multiplayer Commander needs separate evaluation/opponent assumptions. It is not ordinary chess minimax. |
| Easy makes random mistakes 20% of the time | Use reproducible seeded variation among plausible legal choices. Do not hardcode an untested probability, issue illegal actions, fabricate a pass or arbitrarily break mandatory decisions. |
| Hard computes win probabilities | Call an uncalibrated score a positional/strategic evaluation. A numeric heuristic is not an empirical probability or proof of optimal play. |
| Zero lag and 100% offline | Aim for responsive interaction, bounded thought and tested offline operation. Cache the exact engine, card/rules data, CPU policy and chosen deck. First-download, cold-start and decision costs still exist. |
| Animate the chosen action and tap its lands | Render accepted engine events. Never move cards, reveal hidden faces or tap guessed sources before rules commit. Mana previews/payments come from actual costs and source restrictions. |

Current stats matter: a threat score cannot rely only on printed power/toughness
or mana value. Relevant inputs include effective characteristics, granted
abilities, marked damage, counters, attachments, attack/block restrictions,
resources, timing, and the supported deck's conditional closing plan. The engine
must supply or simulate these facts; the UI/wiki must not guess them.

## Useful references found

1. **Magic-specific bounded search.** Cowling, Ward and Powley study MCTS with
   determinization, domain-informed rollouts and pruning for a Magic variant.
   They compare fixed decks and report improvements over their baseline. This
   supports investigating deck playbooks and selective search; it does not
   prove coverage of arbitrary modern cards or every generated deck.
   [Paper and abstract](https://eprints.whiterose.ac.uk/id/eprint/75050/).
2. **Hidden-information search.** Cowling, Powley and Whitehouse's ISMCTS work
   models information sets and explains why naive determinization can choose
   inconsistent plans across hidden worlds (strategy fusion). Sampling alone
   is not a fairness or playing-strength proof.
   [Paper](https://eprints.whiterose.ac.uk/id/eprint/75048/).
3. **Multiplayer search.** Sturtevant's comparison discusses limitations of max-n
   pruning and compares it with a paranoid opponent model across several games.
   The useful lesson is to test the multiplayer policy explicitly rather than
   assuming a two-player adversarial model transfers unchanged.
   [Author's abstract](https://www.cs.du.edu/~sturtevant/papers/sturtevant2002comparison.html).
4. **Worker execution.** The HTML Standard defines background workers and message
   passing independently of UI scripts. Use a bounded worker, cancellation and
   revision-tagged messages; a worker does not make computation free or promise
   zero frame stalls under all memory/CPU conditions.
   [Standard](https://html.spec.whatwg.org/dev/workers.html).
5. **Existing tactical code to study.** Forge's combat helper queries effective
   combat damage, legal attackers/blockers, prevention and keyword interactions.
   Its mana helper separates payment testing from execution and scores the
   opportunity cost of using mana sources with other abilities or combat use.
   These are useful examples of engine-aware heuristics. The inspected combat
   source carries GPLv3-or-later notices; this is reference study, not code
   imported into CardStashy or a decision to adopt its runtime.
   [Combat](https://github.com/Card-Forge/forge/blob/master/forge-ai/src/main/java/forge/ai/ComputerUtilCombat.java)
   · [Mana](https://github.com/Card-Forge/forge/blob/master/forge-ai/src/main/java/forge/ai/ComputerUtilMana.java).
   Inspected file blob SHAs: `2b9520cb649238d7bc53ffa1a1309a40598e6f76`
   and `50bf6144de26d852034972b7755788da982e51b0`.

## Proposed CPU contract

The rules authority produces a seat-scoped observation and current legal
choices. The CPU worker receives that packet, a versioned exact-deck playbook,
profile and recorded RNG state. It returns a proposed choice and compact reason
codes. The authority checks the seat, revision, legality and payment, commits
once, and emits the events consumed by the board, log and inspector.

Never send the authoritative saved game to the policy and merely promise not
to read private fields. A search may build hypothetical hidden worlds only
from permitted information. Specify whether full deck composition is public;
knowing a published precon is different from knowing its current hand or future
library order. Preserve legitimately revealed information without granting
knowledge of cards the CPU has never seen.

Decision windows include responses and mandatory choices during the human's
turn. Do not drive the CPU only from a turn-owner flag. The engine decides the
authorized actor and prompt; the UI must not invent that ownership.

Keep a small persistent worker set instead of creating a worker for each card
or action. Measure message/serialization work as well as search.

Use a deterministic node/iteration budget and stable ordering for reproducible
policy tests, with a wall-clock watchdog for responsiveness. Capture the
selected action and any watchdog fallback in the accepted log: a seed alone
cannot reproduce a hardware-dependent early cutoff.

| Profile | Initial implementation direction; requires measurement |
| --- | --- |
| Easy | Fast current-position heuristics, basic development/combat and optional seeded choice variation; all mandatory choices remain legal. |
| Medium | Short sequencing search, threat/interaction priorities, combat evaluation and deck-plan resource discipline. |
| Hard | Deeper bounded iterative search and permitted uncertainty models, with explicit closing/defensive plans. Multiplayer behavior is tested separately. |

Do not introduce depth counts, weights, mistake rates or latency claims as
established facts before paired-seed benchmarks and tactical fixtures.

## Source findings that affect adoption

CardStashy's current mana/deck analysis and learning helpers are useful reuse,
but they are not an integrated authoritative game adapter. The new right-hand
game inspector and accepted-event animation/log pipeline remain gameplay work.
Checked sources include `rule-dex.js`, `rule-learning.js`, `insights.js`,
`mtg-mana-sources.js`, `goldfish.js`, `deck-experience.js` and `desktop-play.js`.
Do not repurpose heuristic deck Power or matchup estimates as a live board
evaluation or calibrated probability of winning.

Phase is still only a candidate at commit
`71ccd8fe1715c45fe9e9bd78d391bec5ac8a4234`. Its presets explicitly use
`determinization_samples = 0` and its default search uses the authoritative state.
Its WASM proposal call uses `rand::rng()`. Thus its default CPU fails our stated
fairness/reproducibility requirements. Neither enabling sampling nor seeding
only the game shuffle closes that finding. See the [engine evaluation](4.0-engine-evaluation.md)
and the pinned upstream `config.rs`, `determinize.rs`, `search.rs` and WASM bridge.

There are useful building blocks to evaluate rather than recreate: engine-owned
legal actions and payment previews, filtered state, revision-bound proposals,
archetype/strategy weights, bounded beam-plus-rollout search, iterative deepening
and a measurement mode with no wall-clock cutoff. The inspected Medium preset
uses depth 2 / 24 nodes / branching 5; Hard uses depth 3 / 48 nodes / branching 5.
These are source settings, not validated CardStashy profiles. Its shared search
budget constant is 1,500 ms, which is neither zero latency nor a measurement of
complete move/render time. Reuse requires the fairness, seed and runtime gates
above; no preset is approved solely because its labels resemble the proposal.

The pinned nightly Rust toolchain and wasm-bindgen CLI 0.2.121 were installed
in an isolated research workspace. Both source builds were killed at the
8 GiB container limit: the original two-job `wasm-dev` build and the serial
unoptimized/no-debug retry (`SIGKILL`; cumulative cgroup `oom_kill = 2`). This
is a compiler-resource finding, not a gameplay memory or latency measurement.

A completed upstream WASM artifact for the exact inspected commit was then
retrieved and its archive checksum verified. The runtime booted in Node with
fetches forbidden. Six seeded full games (three seeds with each starting
player) reached engine GameOver; a fresh process restored an action-80 Priority
save and reproduced every remaining accepted action and the same outcome.
Both seats used our tiny ungraded legal-action smoke policy, not the upstream
CPU. The lists contain only Forest and Grizzly Bears and are deliberately
land-heavy. This is feasibility evidence, not contextual strategy or support
for every generated deck. All six winners were seat 1; no strength/balance
conclusion follows.

Initial viewer projections hid unknown names/card IDs and zeroed the game RNG
seed/position in both seats. They retained ordered opaque library object IDs.
That observation is not a confirmed identity exploit, and this limited check
is not the required hidden-world equivalence audit. Build a whitelisted CPU
observation rather than exposing an entire UI state/save or raw event stream.
The saved state remains authority-only.

The optional [reproducible harness and evidence](../experiments/phase-engine/README.md)
record exact hashes, action-trace hashes and test limits. No candidate runtime
has been added to CardStashy's product assets. Browser cold-offline recovery,
tactical correctness, fair graded CPU behavior and the full release gate are
still open.

## Required evidence before calling this working

- Privacy: change only unseen opponent cards/future draws while keeping the
  permitted observation and decision seed identical; require identical candidate
  packets/decisions and no private fields in policy packets or logs.
- Tactics: engine-backed removal, protection, counters/layers, attachments,
  combat trades, lethal lines, holding interaction and deck-specific prerequisites.
  Never replace a difficult mechanic with a manual legal-looking action.
- Difficulty: same legal rules/knowledge, versioned policies, paired seeds and
  independent fixtures; calibrate strength and randomness separately from speed.
- Responsiveness: cold/warm startup, decision p50/p95/worst-case, main-thread
  frame cost, cancellation, maximum decision work and peak memory on supported PC devices.
- Recovery: complete games in both seats, cold offline create/save/terminate/
  restart/resume at pending choices, and replay without duplicate moves/results.
- Coverage: declare the exact format/player count/card pool, then separately
  validate precons, meta, random and personal decks. Two test decks establish
  feasibility only. The full Play UI remains behind the existing engine gate.
