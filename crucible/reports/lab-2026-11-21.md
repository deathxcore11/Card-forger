## What Version 27 changes

- **A saved run is never erased by starting another.** Descend with a run saved shows
  "You have a run in progress": resume it, or bank it as it stands and start anew.
- **A failed save is shown.** A "Not saved" bar with Try again stays until the write
  succeeds. The profile is written first; the saved run is removed only after that write is
  stored, so closing the page at any moment loses neither.
- **Each run is banked once.** The page names each run; the profile keeps the last 40 names
  and refuses one it has seen. A finished run found on disk at start-up is banked then.
- **Leaving banks the run as a loss.** A new engine action `abandon` ends the run from any
  screen. The page says what is kept before the player confirms. A run left before any duel
  was won or lost pays nothing, so starting and leaving cannot mint Memories.
- **Saved data that cannot be read is set aside**, under `<key>.unreadable`, and the page
  says so. It was thrown away before.
- **The Winnower.** The merchant cuts a card out of the deck, not the trunk: 15 Embers,
  never a bound meld, never below 34 cards. The engine id is still `scrapper`. The door
  text is part of hashed run state, so fixture run 901 was remade for the wording only.

Decisions made here, the owner may overturn: a run left before any duel pays nothing; a
deck never goes below 34; there is no leave control inside a duel (the chamber screens
have it).

## Fact check of the review of Version 27 (the owner's second assistant)

Each finding was reproduced in a browser on the published Version 27 build before anything was changed.

| Finding | Verdict | What I saw on Version 27 | State |
|---|---|---|---|
| An old tab can delete a newer run | Real | Two pages of one browser profile. Page 1 banked the run and began a new one; Abandon in page 2 removed the new run. An ordinary move in page 2 wrote the old run over the new one. A profile write from the page that was behind undid the other page's bank. Nothing was paid twice, as the review said | Fixed |
| Some damaged saves still crash | Real, one case worse | An unknown phase offered Continue and stopped the page ("is not a function"). A finished run with missing tallies stopped the page at start-up. A finished run with an empty result did not crash: it was banked for 25 Memories | Fixed |

| The pack promises at least 5 Memories every run | Real | A run left before its first duel pays nothing, by the Version 27 ruling | Pack corrected |

What changed:

- **Two tabs.** A new stored value (`lostmemories.runrev.v1`) says which run is stored and how many times it has been
  written. Before a tab makes a move it checks that the stored run is still the one it is showing. If not, it changes
  nothing and says "This run moved on" with one button back to the start, where Continue picks up the current run.
  Banking removes the stored run only if it is the run being banked. Each tab takes in the stored profile before it
  changes its own copy, and a `storage` event does the same as soon as the other tab writes.
- **Damaged saves.** `crucible/web/saves.mjs` holds the check: a known phase, the numbers and lists the page reads,
  cards that exist, and what each phase needs (doors of known kinds, a duel with both sides, an offer, a result with
  a reason). A run that fails is set aside under `<key>.unreadable`, never played and never banked. 702 saves written
  by earlier builds all pass it, and so does every state of six simulated runs.
- **Damage the check cannot see.** Showing the page and making a move are now guarded. If either fails the page goes
  back to the start and says so. The stored run is kept unless it could not even be shown after Continue, or failed
  a move twice running; then it is set aside. Each such fault is still reported as a page error beginning
  "recovered:", so the click bot and the checks keep counting them.

Limits: two tabs are told apart by reading shared storage, which has no lock. Two taps in two tabs within the same
few milliseconds could still collide. A person cannot do that by hand.

## A browser that hands the page an empty store for one load

Found by the click bot on the candidate build: one saved game of 92 reported "no Continue after
reload". Followed until the cause was seen.

- **What happens.** The bot reloads the page in the middle of a run. About once in 100
  reloads, with four test browsers running at once, the page that loads finds the browser's store
  empty: no run, no profile, no key at all. Recorded on one such reload: six keys in the store just
  before it, none after it, none one second later, and all six again after one more reload.
  Nothing was lost; one load of the page was handed an empty store.
- **It is not new and not from today's changes.** The published Version 29 does it at the same
  rate (3 in 238 stressed reloads). The page never clears the store; it has no code that could
  remove the profile at all.
- **It needs the game page.** A blank page that writes more data, faster, through 800 reloads in
  the same four-at-once set-up never showed it. I do not know why the game page brings it out
  (it is large, and it reads the store while it is still loading). Whether an ordinary browser on
  a phone ever does this is **not assessed**; it has only been seen in the headless test browser.
- **Why it matters anyway.** A page that believes the empty store begins a new profile. Its first
  save would then write that new profile over the real one, and a new run over the saved run.
- **The guard.** The tab remembers (in the session store, which a reload keeps) that the store
  held something. If the store then comes back with nothing at all in it, the page draws only a
  notice, "Your saved progress did not load", with Load the page again and Start without it, and
  every write is refused until the player chooses. A first visit, with nothing remembered, starts
  as usual. This covers a reload in the same tab, which is where it was seen. A page opened fresh
  in a new tab has nothing to remember and is not covered.
- **Checks.** Six new save checks (87): the notice shows, nothing is written, loading again finds
  the run and the profile as they were, a first visit is unaffected, Start without it works and
  the notice does not return. Version 29 fails two of them. Under the same stress the guarded
  build met the empty store twice in 251 reloads: both times the notice showed, nothing was
  written, and the run carried on after the second load. The bot now counts these and says so.

## Phase 3, second piece: Two builds a run (Lab switch `builds`, off)

The finding it answers: engines of two and three relics rarely come together. A run gives five
Gifts, the pool holds four big builds (Storm, Tomb, Ambush, Furnace), and a player who wants one
of them is mostly offered pieces of the other three.

With the switch on (lever `runBuilds: 2`):

- Each descent carries the Gifts and charms of two of the four big builds. The two come from
  the run seed on a stream of their own, so the same seed deals the same kits, doors and rivals
  with the switch on or off (a rule test holds this).
- The kit screen names the two builds before a kit is picked, and every Gift offer names them
  again. The "Sets off" line on an offer leaves out Gifts the run cannot offer.
- Lean Deck, plain and trade pieces are in every run. A Linked relic is offered when either of
  the builds it joins is carried.
- The Veilwalker's descent always carries Ambush (her tag is "Veiled monsters and Traps"; a
  Veilwalker run with no Ambush Gifts would be a run against her own rule). The other three
  Forgers have no build of their own. A newly unlocked Gift's build is always carried too, so
  the Gift can be shown; in the rare run where those ask for three builds the run carries three.
- Still five Gifts a run.

Reading:

- It does what it was built for. The committed player ends with about one more piece of its
  build, more than half its runs end with five or more, and the long chains of relic effects
  come nearly twice as often.
- Runs get about two to three points easier. Each gap alone is at the edge of what 3,000 runs
  can tell apart (about two points), but all three comparisons point the same way, so I take it
  as real and small. Not tuned away yet: the switch is off, and the right answer depends on
  whether a person finds the runs better.
- The cost: relics of two different builds set each other off less often (0.21 against 0.34 a
  duel), because a run holds fewer builds. Linked relics, which exist to join builds, still
  work with it (0.49 a duel with both on, against 0.55 with Linked relics alone).

### Faults found while building it

1. The simulator's new player crashed every run (`FAMILIES[opts.family]` with a family that is
   decided per run). Fixed with `familyOf(run, family)`.
2. A picture of a Gift offer in a run carrying Tomb and Ambush said "You hold Storm pieces" and
   "Sets off: Chain Lightning": charms were not filtered and the sets-off line named Gifts the
   run could never offer. `carries(run, id)` now holds for Gifts, charms and that line. A rule
   test plays whole runs and fails if any offer holds a piece of a build the run does not carry.
3. A Veilwalker run could be dealt two builds with no Ambush. Fixed as above, with a rule test.
